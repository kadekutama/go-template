### CR-001 — `toUnleashEvalContext` Omits `targetingKey`, Breaking User and Tenant Targeting [High] [Confirmed]
- **Location:** `internal/infrastructure/featureflag/unleash.go:505-541` — `toUnleashEvalContext`
- **Issue:** In `toOpenFeatureContext` (`unleash.go:238-254`), `evalCtx.UserID` (or `evalCtx.TenantID` if `UserID` is empty) is passed as the targeting key to `openfeature.NewEvaluationContext(targeting, attrs)`. The OpenFeature SDK places this into `FlattenedContext` under the key `"targetingKey"` (`openfeature.TargetingKey`). However, `toUnleashEvalContext` maps keys using:
  ```go
  switch key {
  case "AppName":
      unleashCtx.AppName = val
  case "CurrentTime":
      unleashCtx.CurrentTime = val
  case "Environment":
      unleashCtx.Environment = val
  case "RemoteAddress":
      unleashCtx.RemoteAddress = val
  case "SessionId":
      unleashCtx.SessionId = val
  case "UserId":
      unleashCtx.UserId = val
  default:
      custom[key] = val
  }
  ```
  Because `"targetingKey"` is not handled, it falls into `default: custom["targetingKey"] = val`. `unleashCtx.UserId` is left as an empty string.
- **Why it matters:** Any Unleash strategy targeting user IDs (e.g. percentage rollouts by user ID, user allowlists, or canary cohorts) fails to evaluate against the intended user.
- **Evidence:** `internal/infrastructure/featureflag/unleash.go:238-254` vs `unleash.go:520-535`, confirmed against OpenFeature Go SDK `openfeature/client.go:774` (`flatCtx[TargetingKey] = evalCtx.targetingKey`).
- **Plan violation:** Requirement `E10-T01-R01` ("evaluation context (user/tenant/custom attrs)") and `SPEC.md §7.6`.
- **Expected behavior:** In `toUnleashEvalContext`, `key == openfeature.TargetingKey` (or `"targetingKey"`, `"UserId"`) should map to `unleashCtx.UserId` when user ID was provided.
- **Recommended fix:** Add `case openfeature.TargetingKey, "targetingKey", "UserId": unleashCtx.UserId = val` in `toUnleashEvalContext` (or set `unleashCtx.UserId` accordingly).
- **Verification:** Unit test passing an `openfeature.FlattenedContext{openfeature.TargetingKey: "usr_123"}` to `toUnleashEvalContext` and asserting `unleashCtx.UserId == "usr_123"`.

### CR-002 — `Fallback.cache` (`appport.Cache`) Is Write-Only; Cache Is Never Read on Miss/Restart [High] [Confirmed]
- **Location:** `internal/infrastructure/featureflag/fallback.go:96-121` — `Fallback.Resolve`
- **Issue:** `Fallback.Observe` writes the flag value to `f.cache.Set(ctx, fallbackCacheKey(key), encoded, fallbackCacheTTL)`. However, `Fallback.Resolve` only checks its in-memory map `f.entries[key]` and static `f.defaults[key]`. It never calls `f.cache.Get`. Furthermore, `Resolve(key string, def bool)` does not accept a `context.Context` parameter required to call `port.Cache.Get(ctx, ...)`.
- **Why it matters:** On cold start or process restart, `f.entries` in memory is empty. If Unleash is unreachable upon startup, the service cannot serve the last-known value persisted in the shared L2 cache (`appport.Cache` / Valkey). Instead, it falls back immediately to hardcoded defaults. The doc comment at lines 18-20 ("shared-cache copies expire after one hour so cold starts can serve a value marked stale until the next successful refresh") is unfulfilled.
- **Evidence:** `internal/infrastructure/featureflag/fallback.go:96-121`. `f.cache` is only referenced on line 86 (`if f.cache != nil`) in `Observe`. `Resolve` has no reference to `f.cache` whatsoever.
- **Plan violation:** Requirement `E10-T01-R03` ("Fallback provider MUST serve last-known values or configured defaults when Unleash is unreachable; fallback MUST be Valkey-backed or in-memory") and scenario `E10-T01-S03`.
- **Expected behavior:** When `f.entries[key]` misses in memory, `Fallback` should attempt to retrieve the last-known value from `f.cache` if configured (with appropriate context or pre-warm), and populate `f.entries` before falling back to defaults.
- **Recommended fix:** Update `Resolve` (or add an L2 lookup method accepting context) to check `f.cache.Get` when an in-memory entry is absent, or pre-warm in-memory entries from cache during initialization.
- **Verification:** Unit test where `f.entries` is empty, `f.cache` has a pre-populated key, and calling resolve returns the cached value with `Fallback: true`.

### CR-003 — Provider Outages / Missing Flags Evaluated via `UnleashEvaluator` Return Default as Fresh Success (`Fallback: false`), Overwriting Last-Known Values [Medium] [Confirmed]
- **Location:** `internal/infrastructure/featureflag/unleash.go:344-353` (`unleashProvider.BooleanEvaluation`) and `internal/infrastructure/featureflag/client.go:120-124` (`Client.BooleanWithDetails`)
- **Issue:** When Unleash is evaluated via `unleash.IsEnabled(flag, unleash.FeatureOptions{Ctx: unleashCtx, Fallback: &defaultValue})`:
  1. If a flag does not exist in Unleash or if background polling failed, `unleash.IsEnabled` returns `defaultValue` without error.
  2. `unleashProvider.BooleanEvaluation` packages this into `valueDetail(res, "", map[string]any{"enabled": res})`, which has `ResolutionError: nil` and no `Reason` indicating default or fallback.
  3. Consequently, `openfeature.Client.BooleanValue` returns `(defaultValue, nil)`.
  4. In `Client.BooleanWithDetails`, `value, err := c.evaluateWithResilience(...)` sees `err == nil`.
  5. It executes lines 121-123:
     ```go
     c.fallback.Observe(ctx, key, value)
     return appport.FlagDetails{Value: value}, nil
     ```
  6. This returns `FlagDetails{Value: value, Fallback: false, Stale: false}, nil`.
- **Why it matters:**
  - Callers receive `Fallback: false`, incorrectly indicating the value is fresh from Unleash targeting, when it actually fell back to `defaultValue`.
  - Calling `c.fallback.Observe(ctx, key, value)` overwrites any valid, genuine last-known value in `c.fallback` with the unproven default.
  - The circuit breaker is not aware of the missing flag or polling outage during evaluations because `err` is `nil`.
- **Evidence:** `internal/infrastructure/featureflag/unleash.go:344-353` and `client.go:120-124`. Unit tests masked this because `client_test.go` used `stubEvaluator` with pre-set `evalErr: providerUnavailable()`, rather than exercising `UnleashEvaluator`.
- **Plan violation:** Scenarios `E10-T01-S03` ("Fallback serves last-known value + fallback marker") and `E10-T01-S04` ("Fallback serves configured default + fallback marker with typed provider-unavailable error").
- **Expected behavior:** When Unleash does not have the flag in its repository or has not successfully fetched toggles, `BooleanEvaluation` should return an appropriate `ResolutionError` (e.g. `openfeature.NewFlagNotFoundResolutionError` or check toggle existence in Unleash storage/snapshot), or return `openfeature.DefaultReason`, so `Client.BooleanWithDetails` can serve fallback with `Fallback: true` and avoid overwriting last-known values.
- **Recommended fix:** Inspect whether the flag exists in the Unleash client's toggle repository before returning `valueDetail`. If the toggle is missing, return a `FlagNotFound` resolution error or indicate default reason so that `Client` routes to fallback and does not overwrite last-known state.
- **Verification:** Integration test with `UnleashEvaluator` querying an unregistered flag and verifying that `BooleanWithDetails` returns `Fallback: true`.

### CR-005 — `UnleashEvaluator.Close` Relies on Panic Recovery Rather than `sync.Once` [Low] [Confirmed]
- **Location:** `internal/infrastructure/featureflag/unleash.go:223-227` — `UnleashEvaluator.Close`
- **Issue:** `UnleashEvaluator.Close` implements idempotent shutdown by recovering from panics when `e.provider.Shutdown()` is invoked repeatedly:
  ```go
  defer func() {
      if recovered := recover(); recovered != nil {
          err = nil
      }
  }()
  e.provider.Shutdown()
  ```
- **Why it matters:** Panic recovery during normal lifecycle operations masks genuine unexpected panics (e.g. nil dereferences) and is anti-idiomatic in Go. A `sync.Once` cleanly guarantees single execution without suppressing runtime failures.
- **Plan violation:** None identified.
- **Expected behavior:** Idempotent close operations should be synchronized via `sync.Once`.
- **Recommended fix:** Guard `e.provider.Shutdown()` with a `sync.Once` inside `UnleashEvaluator` or `unleashProvider`.
- **Verification:** Inspect `Close` implementation and verify concurrent close calls succeed without panicking.

### CR-009 — Coarse `sync.RWMutex` on Read-Heavy Fallback Cache Instead of Atomic/Lock-Free Structure [Low] [Confirmed]

### CR-012 — Hot-Path Mutex Contention and Data Race Caused by Two-Stage `Init` and Dynamic Lifecycle Check [Medium] [Confirmed]
- **Location:** `internal/infrastructure/featureflag/unleash.go:270-342, 364-372, 540-572` — `Init`, `ensureReady`, `BooleanEvaluation`
- **Issue:**
  1. **Two-Stage Initialization:** `newUnleashProvider` does not instantiate `unleash.NewClient`; instead, it defers client construction to `openfeature.StateHandler.Init`. Consequently, `p.client` and `p.status` remain mutable fields on `unleashProvider` requiring mutex protection (`p.mu`).
  2. **Hot-Path Mutex Contention:** In `BooleanEvaluation`, line 364 invokes `p.ensureReady()`. Every single evaluation on every inbound request locks and unlocks `p.mu` (`p.mu.Lock()`, `defer p.mu.Unlock()`) merely to check whether `p.status == openfeature.ReadyState`. In high-throughput multi-core services, this creates substantial CPU cache-line bouncing and lock contention on the hottest read path.
  3. **Unsynchronized Read (Data Race):** In `BooleanEvaluation` line 366:
     ```go
     if p.status != openfeature.ReadyState {
     ```
     `p.status` is read *outside* `p.mu`, while `setStatus` (line 550) and `Shutdown` (line 330) write `p.status` under `p.mu`. Concurrent evaluation and shutdown trigger an unsynchronized data race.
- **Why it matters:** Severe concurrency bottleneck on the critical flag evaluation path, accompanied by an unsynchronized data race between evaluations and provider shutdown.
- **Plan violation:** `AGENTS.md` Concurrency & Clean Architecture principles.
- **Expected behavior:**
  - `unleash.NewClient` should be constructed directly in `NewUnleashEvaluator` and passed to `newUnleashProvider`. `p.client` becomes an immutable pointer set at construction.
  - Readiness in Unleash v6 is signaled via the channel `client.Ready()`. In Go, checking whether a channel is closed via `select { case <-p.client.Ready(): return true; default: return false }` is **natively non-blocking, thread-safe, allocation-free, and lock-free**.
  - A mutable `p.status` and hot-path `p.mu.Lock()` in `ensureReady()` are completely unnecessary.
- **Recommended fix:** Initialize `unleash.NewClient` in `NewUnleashEvaluator`, pass the immutable client to `unleashProvider`, eliminate `p.mu` and `p.ensureReady()`, and use lock-free `select { case <-p.client.Ready(): ... }` for readiness checks.
- **Verification:** Inspection of `unleashProvider` showing zero mutex locks on the `BooleanEvaluation` path, and running race detector tests with concurrent evaluations during shutdown.
