## Findings

### CR-005 — RBAC threshold silently disables the approver rule when unconfigured [Medium] [Confirmed]
- **Location:** `internal/infrastructure/auth/rbac/enforcer.go:181` — `Enforcer.evaluate`
  (`if attrs.AmountMinor > e.threshold && e.threshold > 0`)
- **Issue:** With `ThresholdAmountMinor <= 0` (the zero value; `RBACParams` carries no
  validation and `NewEnforcer` validates nothing), the approver ≠ resolver rule never
  applies — any amount can be resolved and approved by the same actor.
- **Why it matters:** A deployment that omits the threshold boots and runs without the
  E04-T02 dual-approval control on money movement above *any* amount — a fail-open
  authorization default that contradicts the packet's default-deny posture and the
  zero-silent-defaults doctrine (ADR-021, still Proposed) the same round introduced.
- **Evidence:** `evaluate` returns early ("approver must differ…") only when both
  conditions hold; nothing rejects a non-positive threshold at construction; tests only
  ever construct `ThresholdAmountMinor: 100000`.
- **Plan violation:** E09-T03-R02 intent ("Above-threshold money actions MUST require an
  approver distinct from the resolver"); ADR-021 §1 (proposed).
- **Expected behavior:** Missing/invalid threshold configuration fails fast at
  construction; or an explicit opt-out (documented in the packet) is the only way to
  disable the rule.
- **Recommended fix:** Validate `ThresholdAmountMinor > 0` in `NewEnforcer` (per ADR-021),
  or add an explicit `AmountGuardDisabled bool` documented in the packet amendment.
- **Verification:** Unit case: `NewEnforcer` with `ThresholdAmountMinor: 0` → constructor
  error (or a test proving the rule still engages when configured).

### CR-006 — Durable DB policy loader targets a `casbin_rules` table no migration creates [Medium] [Confirmed]
- **Location:** `internal/infrastructure/auth/rbac/db_loader.go:91,116-118` —
  `CasbinRuleModel.TableName` / `DBPolicyLoader.Load`
- **Issue:** The loader queries a `casbin_rules` table, but no migration under
  `internal/infrastructure/database/migration/versions/` creates it (verified across all
  nine SQL files), and no GORM AutoMigrate call exists for `CasbinRuleModel`.
- **Why it matters:** The packet amendment (2026-09-25) advertises "durable database
  policy storage in addition to CSVLoader" and ADR-020 §6 records the same; at runtime
  the first `Load()` fails with a missing-relation error wrapped as `ErrPolicyInvalid`.
  `loader_test.go` proves only the disconnected-DB error path and the table-name
  constant — the advertised capability is untested and non-functional.
- **Evidence:** `grep casbin_rules` matches only `db_loader.go` and `loader_test.go`;
  no `CREATE TABLE casbin_rules` anywhere in the migration tree.
- **Plan violation:** E09-T03 packet Amendment 2026-09-25; ADR-020 §6.
- **Expected behavior:** A migration creates `casbin_rules` (with RLS if tenant-scoped)
  and an integration test proves `ReloadFrom(DBPolicyLoader)` round-trips policies.
- **Recommended fix:** Add the table DDL under the migration-owning task's coordination
  (reserve the migration number in a reopened claim per SDD §6), then add the
  Testcontainers test.
- **Verification:** `go test ./internal/infrastructure/auth/rbac/ -run TestDBPolicyLoader`
  against Testcontainers PostgreSQL after `runner.Up`.
