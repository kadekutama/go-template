## Findings

### CR-007 — `SnapshotProvider.Swap` can silently drop a concurrent rotation's key [Low] [Risk]
- **Location:** `internal/infrastructure/auth/jwt/keys.go:73-88` — `SnapshotProvider.Swap`
- **Issue:** `Swap` is a Load → merge → Store sequence with no CAS loop; the comment claims
  "concurrent swaps merge by kid, never tear reads", but two concurrent swaps can each load
  the same current snapshot and the later `Store` wins, discarding the other writer's key.
- **Why it matters:** A lost kid makes tokens signed by that kid fail closed (valid tokens
  rejected until the next reload) — a fail-closed availability gap, not a security hole.
  The design elsewhere states rotation is serialized by the caller (Redlock, E08-T02);
  if that contract holds, the race cannot fire, but the comment overclaims safety.
- **Evidence:** `keys.go:76` loads the current snapshot, mutates a merged copy, and
  `keys.go:87` stores it — no compare-and-swap or single-writer enforcement in code.
- **Plan violation:** None identified (packet does not specify concurrent-rotation semantics;
  E09-T01-R03 covers overlap/JWKS, which is implemented correctly).
- **Expected behavior:** Either a CAS retry loop (Load/Store with pointer comparison) or a
  documented, enforced single-writer contract replacing the current comment.
- **Recommended fix:** Add a CAS loop around the snapshot pointer, or correct the comment
  to state the single-writer (Redlock) precondition explicitly.
- **Verification:** Unit test: two goroutines `Swap` distinct kids concurrently; assert
  both kids remain in `ActiveSet()` — today this can intermittently fail.
