## Findings

### CR-001 — Parity baseline provenance is not durable (checksum/provenance claims absent from fixture and test) [Medium] [Confirmed]
- **Location:** `internal/infrastructure/auth/rbac/testdata/authorization-parity.json` (whole file) and `internal/infrastructure/auth/rbac/version_parity_test.go:37-46,94-129` — `loadParityFixture`, `TestAuthorizationDecisionsMatchBaseline`
- **Issue:** The fixture holds only `cases`; there is no `module`, `version`, `role`, or `live_pin` field, and the test asserts no provenance. Yet `tasks/evidence/E09.1-T06.md` ("fixture + v2 checksum written"; owner-round "Fixture `module`/`version` fields confirmed as pre-upgrade baseline by design; made self-describing (`role` + `live_pin` asserted by the test)"), `tasks/handoffs/E09.1-T06.md` ("fixture + checksum checked in", "the fixture is now self-describing (`role` + `live_pin`, asserted by the parity test)") and ADR-025 ("(with the exact v2.8.0 module checksum)") all describe fields and assertions that do not exist in the check-in. No v2.8.0 module checksum is recorded anywhere in the durable task artifacts.
- **Why it matters:** The parity guarantee ("any allow/deny delta vs v2 is a migration bug") is only as credible as the baseline's tie to the v2.8.0 module. Without a recorded checksum/provenance, a later regeneration, corpus edit, or capture from the wrong module is undetectable, and the current acceptance evidence overstates what is durable. For an authorization (protected-core) migration this is exactly the gap the packet's step-2 design was written to prevent.
- **Evidence:** Full read of `authorization-parity.json` (84 lines: only `{"cases":[…10 rows…]}`); full read of `version_parity_test.go` (no provenance assertions); the three artifact quotes above; `tasks/evidence/E09.1-T06.md` contains no checksum value either.
- **Plan violation:** E09.1-T06-S04 ("testdata … captures fixed-case decisions and records the exact v2.8.0 module checksum"); packet step 2 ("preserve the fixture and v2 checksum").
- **Expected behavior:** The v2.8.0 module checksum (e.g., `go mod download github.com/casbin/casbin/v2@v2.8.0` + `sha256sum` of the module zip, or `go.sum`-corroborated `/v2@v2.8.0` hashes recorded verbatim) and the fixture's `role`/`live_pin` self-description exist durably — either as fixture fields asserted by the test (as the artifacts already claim) or as an explicit, re-derivable provenance block in `tasks/evidence/E09.1-T06.md`.
- **Recommended fix:** Smallest fix: add the provenance fields to the fixture JSON (module path, version v2.8.0, checksums, capture date, generation role) and extend `TestAuthorizationDecisionsMatchBaseline` to assert `module == "github.com/casbin/casbin/v2"` and `version == "v2.8.0"` plus a non-empty checksum shape; update the evidence file with the actual checksum value actually used. This keeps the code and parity corpus untouched.
- **Verification:** `go test ./internal/infrastructure/auth/rbac/... -run TestAuthorizationDecisionsMatchBaseline -count=3` after the fixture edit; re-inspect the three artifact claims (ADR-025, evidence, handoff) so every provenance statement matches the recorded state.
