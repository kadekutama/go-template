# Task Specification: E18-T06 — Durable cross-harness code review records

**Last Updated:** 2026-09-28

## Objective

Make code-review outcomes durable and portable across harnesses by defining a
canonical task review artifact, linking it from handoffs, and validating required
reports without invalidating existing task packets.

## Scope

### In Scope

- Add `tasks/reviews/<TASK-ID>.md` to the canonical SDD/interoperability artifacts.
- Define review-record contents, claim/change-surface authorization, lifecycle,
  and handoff linkage.
- Add a task-packet review requirement field and a reusable review template.
- Validate required completed-task review reports with `check-tasks.py --sdd`.
- Add automated tests for the review-record validator and document the workflow.

### Out of Scope

- Re-reviewing completed historical tasks or backfilling their review reports.
- Changing the repository-local reviewer prompt's user-provided content.
- Enforcing reviewer use through a harness-global setting or adding an unrelated
  agent hook.

## Interfaces and Data

- Review artifact: Markdown at `tasks/reviews/<TASK-ID>.md`.
- Packet field: `**Review Requirement:** self|independent|none`.
- Review verdicts: `PASS`, `PASS WITH MINOR ISSUES`, `REVISION REQUIRED`,
  `BLOCKED`.
- No public API, financial data model, database, or migration changes.

## Invariants and Failure Semantics

- A review report is not a substitute for `tasks/evidence/<TASK-ID>.md` or the
  implementation handoff.
- Review reports may be created/updated only when authorized by the active claim's
  Allowed Change Surface; released work follows the SDD reopening/takeover rules.
- An `independent` reviewer's identity must differ from the packet author.
- Only completed tasks with an explicit `self` or `independent` review requirement
  are subject to required-report validation; missing fields in legacy packets are
  treated as legacy/no new check.
- A report with `REVISION REQUIRED` or `BLOCKED` is not an acceptance approval.
