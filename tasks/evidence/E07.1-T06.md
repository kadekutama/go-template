## Measured Citus Limitation (decisive, order-independent)

On a two-node Citus 14.0 cluster with the full schema, only
`idempotency_records` (zero FKs) distributes. Reference-first ordering was
also tried: `create_reference_table('assets')` succeeds alone, but every
later distribution fails — Citus auto-adds FK-connected locals to metadata
and then vetoes (`local/reference → distributed FKs forbidden`,
`relations not colocated`). Per-table causes: accounts/holds (asset FK to
local), postings/entries (triggers), outbox (non-tenant unique). Real
sharding needs FK-constraint redesign + trigger-safe procedure (named
follow-up). Composite PKs remain correct (type safety, tenant uniqueness,
future readiness); the migration stays resilient-by-design with a WARNING
summary (server log; goose clients do not forward server messages).

*Timing & Distribution Addendum (2026-09-18):* Following composite PK modernization,
empirical investigation confirmed that `accounts` local FK does NOT veto `ledgers`
distribution (live counterexample proven: `ledgers`, `idempotency_records`,
`outbox_events`, `audit_refs` all distribute with `accounts` remaining local).
The variance between 3 and 4 distributed tables is timing-nondeterministic rather
than topological: `ledgers` is the first element in `distributed_tables`, and if
worker-sync readiness is still settling when migration 005 begins immediately after
`citus_add_node`, `ledgers` flaps into the resilient EXCEPTION path. Because Goose
applies migrations once, a transiently deferred table remains local permanently.
Identified follow-up hardening: bounded retry with backoff inside migration DO blocks
and an E14 distribution-reconciliation check / deploy-gate assertion.
