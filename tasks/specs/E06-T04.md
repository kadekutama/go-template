## Objective

Back the payments/refunds/payouts API surface: intent lifecycle over the payment-processor port with SCA states, validated refunds with reversal linkage, eligibility-gated payouts with two-stage tracking, and top-ups — with webhook-matching outbox facts, tested with fake processors.

## Scope

### In Scope

- `internal/application/command/{payment,refund,payout}.go`: `IntentService` (create/confirm/cancel/challenge over `port.PaymentProcessor` + consumer-owned `IntentStore`), `RefundService` (window/amount validation via `service.ValidateRefund` + processor execution + consumer-owned `RefundStore`), `PayoutService`/`TopupService` (E03-T11 eligibility gate, two-stage submission shapes, consumer-owned stores).
- `internal/application/query/{payment,refund,payout}.go`: delegating readers.
- `internal/application/dto/{payment,refund,payout}.go`: edge shapes.
- Webhook contract test: emitted outbox event types equal the api-contracts §10 names with id/status payload keys.
- Tests with fake processor (failure leaves PENDING, retry-safe per key) and fakes for stores.

### Out of Scope

- Live processor adapter + sandbox (E10 implements `port.PaymentProcessor`), settlement cron/workers (E14), provider webhooks ingress (E11), sagas (E06-T07), persistence schema (E07-T10 implements the stores).

| ID | Requirement | Priority |

## Invariants and Failure Semantics

- Provider calls happen OUTSIDE `UnitOfWork` callbacks (callbacks stay retry-safe; no provider I/O inside).
- Unknown provider outcomes resolve via `GetStatus` before any money-moving retry (documented; fake proves key reuse).
- Fee refunds default to zero and are explicit, never proportional.
- Unknown commit outcomes resolve via identical resubmission, never blind retry.
