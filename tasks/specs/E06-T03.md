## Objective

Back the transactions/transfers API surface: generic posting transactions, linked reversals, immediate + scheduled + bulk transfers with item independence — over the E03-T01 domain services, tested with fakes.

## Scope

### In Scope

- `internal/application/command/{transaction,transfer,batch_transfer}.go`: `TransactionService` (post delegates to the T13 posting service; reverse via `aggregate.ReversePosting`), `TransferService` (immediate posts now; scheduled persists PENDING; `ExecuteTransfer` enforces funds at execution; cancel; batch intake + per-item execution with `{batch}:{index}` keys), consumer-owned `TransferStore` (E07-T10 implements).
- `internal/application/query/{transaction,transfer}.go`: transaction reads via T13 query services; transfer/batch reads via the store.
- `internal/application/dto/{transaction,transfer,batch}.go`: edge shapes honoring the protocol-parity note (string IDs, minor units, timestamps, status, cursor — everything gRPC/GraphQL need).
- Tests: batch limits (>1000 / mixed-tenant rejected), scheduled PENDING without funds check + execution enforcement, item independence (PARTIAL), replay/conflict, reversal linkage, auth denial.

### Out of Scope

- Sagas (E06-T07), recurrence expansion workers (E14 executes `ExecuteTransfer`), provider settlement (E10), persistence schema (E07-T10 implements `TransferStore`).

## Requirements

| ID | Requirement | Priority |
|----|-------------|----------|
| E06-T03-R01 | Immediate transfers MUST check authoritative available (via `port.GetBalance`) and post debit-source/credit-dest in one `UnitOfWork`; reversals MUST link to the original posting. | must |
| E06-T03-R02 | Scheduled transfers MUST persist PENDING without a funds check; `ExecuteTransfer` MUST enforce funds atomically at execution. | must |
| E06-T03-R03 | Batch intake MUST reject >1000 items and mixed-tenant items; intake is atomic, items execute independently with `{batch}:{index}` keys; sibling failure MUST NOT roll back (PARTIAL, not failure). | must |

## Invariants and Failure Semantics

- One `UnitOfWork` per command/item; item UoWs are independent (no shared atomicity across items).
- IDs minted once before `Do` (retried callbacks reuse; duplicates fail for replay resolution).
- Account/available snapshots load before `Do`; E07 re-validates under locks at commit.
- Unknown outcomes resolve via identical resubmission, never blind retry.
