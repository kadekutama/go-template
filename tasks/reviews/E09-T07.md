## Findings

### CR-002 — Audit `Verify` breaks on any timestamp with sub-microsecond nanoseconds [Medium] [Confirmed]
- **Location:** `internal/infrastructure/audit/chain.go:44-63` — `hashEntry`
  (`occurredAt.UnixNano()`); consumed by `Logger.Verify` at `logger.go:313`
- **Issue:** Entry hashes are computed over `occurredAt.UnixNano()`. On append the
  timestamp may carry nanosecond precision (clock-defaulted in `prepare`, or caller-
  supplied real time); PostgreSQL `timestamptz` stores microseconds, so the value read
  back in `Entries` is truncated/rounded.
- **Why it matters:** For any entry whose timestamp has ns % 1000 ≠ 0 (typical
  `time.Now()` granularity), the recomputed hash in `Verify` differs from the stored
  `entry_hash`, and `Verify` reports `ErrChainBroken` on a **healthy** chain. The
  tamper-evidence feature fails closed as a constant false alarm on production data.
  All tests use whole-second mock clocks, so the path is unexercised.
  `VerifyCheckpoint` is unaffected (it reuses stored `entry_hash` values).
- **Evidence:** `append` hashes the pre-truncation `occurred` (`logger.go:229`); `Verify`
  recomputes from the DB round-trip `entry.OccurredAt` (`logger.go:313`); PG timestamptz
  precision is 1 µs.
- **Plan violation:** E09-T07-R01/R02 intent (the chain must verify against the stored
  chain); no direct packet ID violation.
- **Expected behavior:** `Verify` recomputes hashes over exactly the persisted precision —
  timestamps normalized to microseconds before hashing on both write and verify paths.
- **Recommended fix:** Truncate the timestamp to `time.Microsecond` in `prepare` before
  hashing/storage (single normalization point; both `Record` and `RecordTx` paths).
- **Verification:** Integration test with a clock returning a time with non-zero
  nanoseconds (e.g., `…T00:00:00.000000123Z`): `Record` → `Entries` → `Verify` must pass.

### CR-003 — `VerifyCheckpoint` false-alarms after any legitimate append [Medium] [Confirmed]
- **Location:** `internal/infrastructure/audit/exporter.go:60-62` — `VerifyCheckpoint`
  (`int64(len(chain)) != root.Seq`)
- **Issue:** A checkpoint attests the chain up to `Seq = len(chain)` at checkpoint time,
  but verification demands the *current* chain length still equal that number. Any row
  appended after the checkpoint makes every later `VerifyCheckpoint` against that root
  fail with `ErrCheckpointInvalid`.
- **Why it matters:** The packet's model is periodic signed checkpoints exported to WORM
  while the chain keeps appending (epic step 1; 7y-hot/indefinite-roots posture). With
  the current semantics, checkpoints are verifiable only if nothing was ever appended
  afterwards — producing constant false tamper alarms, or training operators to ignore
  `ErrCheckpointInvalid` (the alert-fatigue failure mode for a tamper-evidence control).
  Deleting rows is still caught (`len < Seq`), so the failure is closed, but the feature
  cannot serve its stated purpose.
- **Evidence:** `VerifyCheckpoint` errors on any length inequality (`exporter.go:60-62`);
  the integration test `TestAuditCheckpointTamperDetection` verifies only immediately
  after checkpointing and actually uses length changes (Seq±1 forgeries) as its
  tamper cases — masking the semantics gap.
- **Plan violation:** E09-T07-R02/R03 (checkpoint verification model); epic step 1
  ("periodic signed Merkle root/checkpoint exported to retention-locked storage").
- **Expected behavior:** `VerifyCheckpoint(root)` verifies the prefix of length
  `root.Seq` (recompute the root over the first `root.Seq` entries), so post-checkpoint
  appends do not invalidate an old checkpoint while truncation (`len < root.Seq`) and
  content tampering still do.
- **Recommended fix:** Slice `chain[:root.Seq]` for the root recomputation (error if
  `len(chain) < root.Seq`); keep the length check only as the truncation detector.
- **Verification:** Integration test: checkpoint → append a third entry →
  `VerifyCheckpoint(oldRoot)` passes; then delete a middle row → fails; shorten the chain
  → fails via `len < root.Seq`.
