## Objective

Ship the first vertical slice: one real financial write/read path — restricted `PostLedgerPosting` through a single `UnitOfWork` plus strongly consistent `GetPosting`, `GetBalance`, and cursor-based `ListEntries` — proven against fakes that model the port contracts.

## Scope

### In Scope

- `internal/application/command/posting.go`: `PostingService` implementing `port.PostLedgerPosting` — envelope validation, command authorization, idempotent reserve/replay/conflict, account-set load, `aggregate.ConstructPosting`, single-`UnitOfWork` commit with outbox fact + idempotency completion, unknown-outcome surfacing without blind retry.
- `internal/application/query/{posting,balance,entries}.go`: strong `GetPosting`, entry-scan `GetBalance` (debts minus credits per asset over committed entries, minus ACTIVE holds), cursor-paged `ListEntries` with clamped limits.
- `internal/application/dto/{posting,balance,entry}.go`: edge DTOs exposing integer minor units, asset code, as-of time, and ledger cursor.
- Tests: happy path, invalid template, unbalanced asset lot, duplicate replay, fingerprint conflict, authorization denial, unknown-outcome, and concurrent same-key attempts (one commit, rest replay) against fakes.

### Out of Scope

- Extended bounded-context handlers (E06-T02–T05/T11), sagas (E06-T07), billing/metering (E06-T10), reporting (E06-T09).
- Database serialization proof (E07 proves with real PostgreSQL; E11-T14 pilots posting → balance → entries end-to-end).
- Materialized balance projections (later adapter optimization; this slice scans committed entries with a documented page cap).

## Invariants and Failure Semantics

- One `UnitOfWork` per command; callbacks are retry-safe (pure construction + tx stores only; IDs minted before Do... see below).
- ID minting before Do keeps callbacks re-runnable: on `Do` retry the same IDs are reused, so a retried callback cannot double-mint. Duplicate posting IDs fail at commit, surfacing as errors for replay resolution.
- Account-set reads happen before Do (construction snapshot); E07 re-validates scope/status under deterministic account locks at commit (data-flow steps 3–5).
- Entry `AccountSeq` is the deterministic 1-based per-account position within the posting (satisfies domain ≥ 1); durable global sequencing is assigned at commit by E07-T01 (data-flow step 5, UNIQUE(account_id, account_seq)) — recorded as E07 follow-up, reversible.
- No workflow state is written to Posting or Entry rows.
