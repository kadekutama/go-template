# Task Specification: E03-T09 — Platform split (destination charges + application fees)

**Task:** E03-T09
**Spec Status:** ready
**Author:** opencode-agent
**Reviewer:** muse-spark
**Last Updated:** 2026-09-15

## Objective

Close Epic E03 with pure platform-split rules: charge on the platform, carve the application fee at charge time, and settle net to the connected account (with explicit FX legs when currencies differ).

## Scope

### In Scope

- `internal/domain/service/platform_split.go`: capture validation (three-leg posting shape per `ledger-core.md §6.1`), hierarchy-grant gating per frozen E05-T02 shape, same/cross-currency settlement legs via E03-T05 `Convert`, and refund reversal with explicit fee-refund policy.
- `internal/domain/service/platform_split_test.go`: strict table-driven unit tests for every requirement and scenario below.

### Out of Scope

- Provider charge submission, persistence, handlers (E06/E07/E10/E11).
- Jurisdiction-specific fee policy (versioned configuration supplied by the caller, not invented here).
- Settlement-time realized gain/loss posting (provider rates arrive via E10; this task records capture-time conversion legs explicitly).

## Normative Inputs

- `tasks/epics/E03-money-movement.md#E03-T09` for the backlog boundary.
- `docs/ledger-core.md §6.1` (capture journal with fee leg: DR Processor Receivable gross; CR Connected Merchant Payable net; CR Platform Fee Revenue fee).
- `docs/money-flow.md §2.10` (fee carved at charge time; settlement in connected currency/region; refund allocation explicit, never assumed proportional).
- `docs/money-flow.md §2.7` (FX conversion legs; gain/loss explicit; lots balance independently).
- `docs/fintech-ledger-features.md §3.5` (destination charges P0, application fees P0, on-behalf-of settlement P1).
- `tasks/specs/E05-T02.md` (hierarchy grant shape frozen as caller-supplied `map[string]bool` keyed by child tenant ID; `ValidateTransferGrant`).
- `internal/domain/service/fx_service.go` (`Convert`, `GainLoss`; half-up, no floats, checked int64 math).

## Requirements

| ID | Requirement | Priority |
|----|-------------|----------|
| E03-T09-R01 | Split MUST validate platform, connected, and processor accounts ACTIVE (frozen/closed/invalid rejected) and MUST require an explicit hierarchy grant for the connected tenant via `ValidateTransferGrant` (`HIERARCHY_GRANT_REQUIRED` without grant, `HIERARCHY_ID_REQUIRED` for empty child ID). | must |
| E03-T09-R02 | Capture posting MUST satisfy gross == fee + net with gross positive and 0 <= fee <= gross (`INVALID_SPLIT_AMOUNT`, `SPLIT_MISMATCH`); processor debit and platform fee legs MUST post in the charge asset (`CURRENCY_MISMATCH` otherwise); the three posting accounts MUST be pairwise distinct (`SPLIT_ACCOUNT_INVALID`). | must |
| E03-T09-R03 | Cross-currency splits MUST convert gross, net, and fee via `Convert` (rate pair MUST be charge asset → settlement asset of the connected account, `FX_RATE_MISSING`/`FX_RATE_MISMATCH`/`FX_RATE_STALE`/`FX_OVERFLOW` propagated); half-up rounding drift MUST post as an explicit gain/loss leg so convertedGross == convertedNet + convertedFee + gainLoss (`SPLIT_FX_UNBALANCED` otherwise). | must |
| E03-T09-R04 | Refund of a split charge MUST reverse all three legs with an explicit caller-supplied fee refund (0 <= feeRefund <= min(refundGross, originalFee), `FEE_REFUND_INVALID` otherwise); refundGross exceeding the original gross MUST fail `REFUND_EXCEEDS_ORIGINAL`; fee refunds MUST never be assumed proportional. | must |

## Executable Scenarios

| ID | Given | When | Then |
|----|-------|------|------|
| E03-T09-S01 | Gross 10000, fee 290, same asset, granted ACTIVE accounts | ValidateSplit | net 9710, gross == fee + net, converted legs equal charge legs, gainLoss 0 |
| E03-T09-S02 | Cross-currency split (charge USD, connected EUR) with fresh rate | ValidateSplit | convertedGross/Net/Fee via Convert, convertedGross == convertedNet + convertedFee + gainLoss |
| E03-T09-S03 | Full refund of an S01 split with feeRefund 290 | ValidateSplitRefund | CR processor 10000 / DR merchant 9710 / DR platform 290; all three legs reversed |
| E03-T09-S04 | Split with no hierarchy grant for the connected tenant | ValidateSplit | `HIERARCHY_GRANT_REQUIRED` |
| E03-T09-S05 | Refund gross exceeding original; feeRefund exceeding policy cap | ValidateSplitRefund | `REFUND_EXCEEDS_ORIGINAL`; `FEE_REFUND_INVALID` |
| E03-T09-S06 | Cross-currency split with stale/missing rate; MaxInt64 gross | ValidateSplit | `FX_RATE_STALE` / `FX_RATE_MISSING`; overflow surfaces `FX_OVERFLOW` |

## Invariants and Failure Semantics

- Immutable postings; this pure function builds lines only, never persists.
- Explicit policy only: grants, fee refunds, and FX rates are caller-supplied; nothing is inferred proportionally.
- Checked int64 arithmetic throughout; overflow errors, never wraps.
- Stable codes: `HIERARCHY_GRANT_REQUIRED`, `HIERARCHY_ID_REQUIRED`, `INVALID_SPLIT_AMOUNT`, `SPLIT_MISMATCH`, `SPLIT_ASSET_REQUIRED`, `SPLIT_ACCOUNT_REQUIRED`, `SPLIT_ACCOUNT_INVALID`, `PLATFORM/CONNECTED/PROCESSOR_ACCOUNT_NOT_FOUND`, `ACCOUNT_FROZEN`, `ACCOUNT_CLOSED`, `ACCOUNT_STATUS_INVALID`, `CURRENCY_MISMATCH`, `FX_RATE_MISSING`, `FX_RATE_MISMATCH`, `FX_RATE_STALE`, `FX_OVERFLOW`, `SPLIT_FX_UNBALANCED`, `INVALID_REFUND_AMOUNT`, `REFUND_EXCEEDS_ORIGINAL`, `FEE_REFUND_INVALID`.
- No external imports in `internal/domain/...` (stdlib + domain only).
