# Task Specification: E03-T11 — Payout eligibility, reserves, and negative-balance recovery

**Task:** E03-T11
**Spec Status:** ready
**Author:** opencode-agent
**Reviewer:** repo-owner
**Last Updated:** 2026-09-14

## Objective

Ship payout eligibility (minimums, first-payout hold, rolling reserve, instant eligibility, strong-cursor available balance) and durable idempotent negative-balance recovery with OUTCOME_UNKNOWN handling.

## Scope

### In Scope

- `internal/domain/valueobject/payout_policy.go`: `PayoutPolicy` per tenant/asset (minimums, 7-day first-payout hold, rolling reserve bps, instant eligibility, version).
- `internal/domain/service/payout_policy.go`: `EvaluateEligibility` reading the strong-projection available balance at a supplied cursor; stable `PAYOUT_BLOCKED` reasons; never reads Valkey/replicas.
- `internal/domain/service/negative_balance_recovery.go`: durable idempotent recovery keyed by tenant/account/asset + idempotency key, verified-instrument gate, OUTCOME_UNKNOWN lookup-before-retry, balanced recovery posting shape + audit facts.

### Out of Scope

- Provider HTTP adapters, SQL schema/transaction (E07/E10 own impl beyond the port-shaped contract here).
- Jurisdiction-specific collections policy: supplied as versioned configuration, not invented (resolves prior draft open question).

## Normative Inputs

- `tasks/epics/E03-money-movement.md#E03-T11` for the backlog boundary.
- `docs/ledger-core.md §7–§8` (strong balance authority, negative availability as policy state, durable idempotency, OUTCOME_UNKNOWN).
- `docs/money-flow.md §5` (minimums, first-payout holds, reserves, negative balances).
- `docs/api-contracts.md §4` (`PAYOUT_BLOCKED`).

## Requirements

| ID | Requirement | Priority |
|----|-------------|----------|
| E03-T11-R01 | Eligibility MUST evaluate minimum, 7-day first-payout hold, rolling reserve, instant-method eligibility, destination verification, and strong-cursor available balance. | must |
| E03-T11-R02 | Ineligible payouts MUST return `PAYOUT_BLOCKED` with a stable reason and MUST NOT submit or post. | must |
| E03-T11-R03 | Recovery MUST key on (tenant, account, asset, idempotency key); same fingerprint MUST replay, different fingerprint MUST conflict. | must |
| E03-T11-R04 | Provider timeout MUST enter `OUTCOME_UNKNOWN` and require status lookup before retry. | must |
| E03-T11-R05 | Confirmed recovery MUST produce a balanced, linked posting crediting the recovery account plus audit and outbox facts; it MUST NOT update a mutable account balance column. | must |
| E03-T11-R06 | New code MUST import only stdlib + `internal/domain/...`. | must |

## Executable Scenarios

| ID | Given | When | Then |
|----|-------|------|------|
| E03-T11-S01 | First payout inside 7-day hold | EvaluateEligibility | `PAYOUT_BLOCKED`/`FIRST_PAYOUT_HOLD` |
| E03-T11-S02 | Available below reserve / negative | EvaluateEligibility | `PAYOUT_BLOCKED` with reason; at most one recovery key |
| E03-T11-S03 | Same-fingerprint recovery replay | StartRecovery twice | same result, one attempt |
| E03-T11-S04 | Provider timeout then retry | RequireLookup then Confirm | lookup required; confirmed recovery balances |
| E03-T11-S05 | PENDING recovery, then COLLECTED recovery | CancelRecovery | pass, then rejected |

## Invariants and Failure Semantics

- Strong projection only (cursor param); cache/replica never authoritative. Stable codes: `PAYOUT_BLOCKED` + reasons `FIRST_PAYOUT_HOLD`, `BELOW_MINIMUM`, `RESERVE_SHORTFALL`, `NEGATIVE_AVAILABLE`, `DESTINATION_UNVERIFIED`, `INSTANT_INELIGIBLE`; `IDEMPOTENCY_CONFLICT`, `OUTCOME_UNKNOWN`.
