## Findings

### CR-004 — Production crypto-shred path is an always-failing stub, yet the epic claims shred "proven" [Medium] [Confirmed]
- **Location:** `internal/infrastructure/crypto/transit.go:214-226` — `TransitKEK.DestroyKey`
- **Issue:** The only production `KeyEncryptionKey` implementation cannot destroy a key
  version: `DestroyKey` unconditionally returns `fmt.Errorf("%w: transit destroy requires
  operator rotation", ErrShredded)`. The shred behavior is proven only against a test
  double (`envelope_test.go` mockKEKState), never against the production adapter.
- **Why it matters:** E09-T06-R04 ("Crypto-shred (destroy key version) MUST make its
  envelopes unrecoverable") and the epic acceptance criterion "Erasure (crypto-shred)
  makes PII unrecoverable while ledger sums hold (test with E04-T04)" are not met on the
  production path — any caller invoking shred through the wired KEK fails. The epic's
  ticked checkbox "[x] … PII round-trip + shred proven" overclaims.
- **Evidence:** The stub body (no HTTP call, `_ = keyID`, unconditional `ErrShredded`);
  `transit_test.go` `TestTransitKEKDestroyKey` asserts exactly that failure shape
  ("destroy fails with ErrShredded operator message"); `envelope_test.go` proves shred
  semantics only via `mockcrypto.MockKeyEncryptionKey`.
- **Plan violation:** E09-T06-R04; packet step 4 ("crypto-shredding path for E04-T04
  erasure"); epic acceptance-criteria checkbox (overclaim).
- **Expected behavior:** The production KEK exposes a working destroy path (Transit
  key-version disable/trim via the engine API) or the packet/ADR records the deferral
  with the risk accepted and the epic checkbox unticked.
- **Recommended fix:** Smallest targeted step: implement `DestroyKey` against the Transit
  engine's key-version management API (or an explicit operator-SOP seam) and amend the
  packet + ADR-016 trail; untick the epic checkbox until the production path is proven.
- **Verification:** httpmock (or integration) test on `TransitKEK`: `DestroyKey` succeeds →
  subsequent `UnwrapDEK` of a version-pinned ciphertext fails with `ErrShredded`, while
  unrelated versions still open.

### CR-011 — Production `UnwrapDEK` ignores the envelope `KeyID`; no version resolution [Low] [Confirmed]
- **Location:** `internal/infrastructure/crypto/transit.go:105-154` — `TransitKEK.UnwrapDEK`
  (`_ = keyID` at line 151); `WrapDEK` returns `k.keyName` as `keyID` (line 101)
- **Issue:** The envelope `KeyID` is the Transit key *name*, never a version; `UnwrapDEK`
  discards the argument and always decrypts against the configured `keyName`. Rotation
  works only because OpenBao Transit ciphertexts embed the version (`vault:v1:…`) and the
  engine resolves it server-side — the adapter performs none of the "decrypt MUST resolve
  the envelope KeyID version" behavior the packet states.
- **Why it matters:** The outcome (old envelopes decrypt after rotation) holds via Transit
  semantics, so this is not a correctness break today — but the packet's R03/S03 mechanism
  is unimplemented, the `_ = keyID` makes the contract implicit, and `RewrapDEK`'s
  `targetKey = keyID` is dead logic (keyID ≡ keyName always). A future multi-key
  deployment would silently decrypt against the wrong key.
- **Evidence:** `WrapDEK` returns `k.keyName`; `UnwrapDEK` discards `keyID`; no test
  exercises a keyID ≠ keyName case; `transit_test.go` covers Wrap/Unwrap/Destroy but not
  `RewrapDEK` at all.
- **Plan violation:** E09-T06-R03 (mechanism, not outcome); E09-T06-S03 (passes via
  server-side version, not "via versioned KeyID").
- **Expected behavior:** Either the adapter resolves versioned key references from
  `KeyID` (e.g., `keyName@version` → Transit decrypt with explicit version), or the
  packet records that Transit's embedded version is the resolution mechanism and drops
  the dead `keyID` plumbing.
- **Recommended fix:** Amend the packet to record the Transit-embedded-version mechanism,
  then either delete the ignored `keyID` plumbing or wire it to a real version selector;
  add a `RewrapDEK` unit test (currently absent).
- **Verification:** httpmock test proving a rotated-key decrypt (ciphertext at v1 after
  key rotation) and a `RewrapDEK` call path.
