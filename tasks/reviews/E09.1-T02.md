## Findings

### CR-001 — Unauthenticated session bootstrap is never rate-limited [Medium] [Confirmed]
- **Location:** `internal/interface/cron/admin/server.go:448-465` — `adminHandler.bootstrap`; route at `internal/interface/cron/admin/server.go:160` (`e.POST("/admin/session", h.bootstrap)`)
- **Issue:** `POST /admin/session` is registered without `limitEnforce`, and `bootstrap` only calls `checkLimit` after the bearer has verified and the subject/scope checks pass (lines 466-472). On the `VerifyBearer` failure path (lines 453-456) the handler returns 401 with **zero** `Allow` calls — the request is never metered, not even against the fixed anonymous bucket.
- **Why it matters:** R05 mandates the limiter for *every* request after Host/Origin validation; ADR-023 §5 says the same. The anonymous bucket exists precisely to meter unauthenticated pressure, and the one endpoint that performs password-class work (JWT verification) admits unfettered retries when authentication fails. Bearer-guessing pressure is invisible to the shared quota.
- **Evidence:** Route registration (server.go:160-161) applies the middleware chain only to `DELETE /admin/session`; `bootstrap` handles POST directly. Read of `bootstrap` shows the first `h.checkLimit` call at line 466, with an early `return c.String(401)` at line 455 that bypasses it. Test `TestSessionBootstrap/unknown_bearer_denied` (admin_test.go:873-877) asserts no cookie and no upstream but never asserts a limiter call — the gap agrees with the code.
- **Plan violation:** E09.1-T02-R05 ("every request MUST consult the … limiter … otherwise the fixed anonymous ID") and its scenario E09.1-T02-S10 ("Protected UI request/session bootstrap … rate key uses opaque subject ID or fixed anonymous ID"); also ADR-023 decision §5.
- **Expected behavior:** Every bootstrap attempt consults the E08-T07 limiter exactly once: bearer-verification failures (and invalid-subject / missing-scope failures) charge the fixed anonymous key; a validated actor charges its own actor key. Denial → 429 + `Retry-After`; store error → 503; both fail closed before admin action.
- **Recommended fix:** Keep the one-charge-per-request invariant: in the `VerifyBearer` failure branch (server.go:453-456), charge the fixed anonymous bucket via `h.checkLimit(r, h.anonymousKey)` immediately before the 401 (auth failure is exactly the case the anonymous bucket exists to meter). Every other code path already performs exactly one `Allow` call (invalid subject / no scope each charge once; valid bootstrap charges the actor key). This keeps authenticated bootstraps metered to their own bucket and untouched by anonymous exhaustion, and cannot double-charge any single request path. Add `TestRateLimit` cases: unauthenticated bootstrap → exactly one `Allow` with the anonymous key + 429 mapping; store error → 503.
- **Verification:** `go test ./internal/interface/cron/admin/... -run 'TestRateLimit|TestSessionBootstrap' -count=3`, then `go test -race ./internal/interface/cron/admin/...` and the integration slice `go test -race ./test/integration/scheduler-egress/... -count=3`.

### CR-002 — Composition Example wires a nil session issuer (27-byte key, swallowed errors) [Low] [Confirmed]
- **Location:** `internal/infrastructure/cronui/compose_example_test.go:83` — `Example_assembleAdminUI`
- **Issue:** `sessions, _ := cronui.NewSessionTokens([]byte("example-key-32-bytes-long!!"))` — the string is 27 bytes, so `NewSessionTokens` (session.go:36-41, guard `len(key) < 32`) returns `(nil, err)`. The error is discarded, leaving `sessionAdapter{tokens: nil}` installed as both `SessionAuthenticator` backing and `SessionTokenIssuer`. Error handling for `NewUpstreamHandler`, `NewSessionTokens`, and `NewBearerTokens` is likewise discarded.
- **Why it matters:** This Example is the documented E14-T01 assembly recipe (ADR-023 "E14 wiring" + handoff). An implementer copying it verbatim inherits a structurally nil issuer that will fail every future bootstrap with 500, and the guard that exists to force ≥32-byte keys is bypassed in the only worked example. It also slightly overstates the "verified composition" claim: the Example proves handler construction only.
- **Evidence:** Key length is static: `example-key-32-bytes-long!!` = 27 bytes. `sessionAdapter.IssueReadSession` (compose_example_test.go:32-38) would call `SessionTokens.Issue` on a nil receiver, which returns `cronui: session issuer is not initialized` (session.go:45-48) — a shipping-time failure, not a construction-time one.
- **Plan violation:** None identified directly (the packet's Interfaces section requires the seams wired by E14; the defect is in the exemplar itself). Tangentially inconsistent with the T02 evidence claim of a "verified composition Example".
- **Expected behavior:** The Example's own wiring should satisfy the guards it teaches: use a genuinely ≥32-byte key, check construction errors (e.g., `panic(err)`-style Example guards or `if err != nil { fmt.Println(...) }`), and document that the returned issuer must be non-nil.
- **Recommended fix:** A 35+ byte literal key plus explicit error checks in the Example; one-line test comment noting how E14 should assert non-nil.
- **Verification:** `go test ./internal/infrastructure/cronui/... -run Example_assembleAdminUI -count=1` after rotation.

### CR-003 — Unauthenticated and un-scoped session bootstraps discard rate limit outcomes and fail open [Medium] [Confirmed]
- **Location:** `internal/interface/cron/admin/server.go:475-483` — `adminHandler.bootstrap`
- **Issue:** In `adminHandler.bootstrap`, when a bearer token has an invalid actor ID (`!valid`) or lacks the required scope (`!hasScope`), `h.checkLimit(r, key)` is invoked but its return values (`allowed, retryAfter, storeErr`) are completely ignored; the method unconditionally returns `c.String(http.StatusForbidden, "forbidden")`.
- **Why it matters:** If the rate limit quota for the anonymous bucket or actor key is exhausted, the endpoint returns 403 Forbidden with no `Retry-After` header instead of 429 Too Many Requests. If the rate limiter store is down, it returns 403 Forbidden instead of failing closed with 503 Service Unavailable, bypassing backoff and quota fail-closed enforcement.
- **Evidence:** Lines 475–483 discard `allowed, retryAfter, storeErr`. Contrast with `denyBootstrapUnauthorized` (lines 446–457) which correctly enforces 503 on store failure and 429 on exhaustion.
- **Plan violation:** E09.1-T02-R05, E09.1-T02-S10, E09.1-T02-S11.
- **Expected behavior:** On `!valid` or `!hasScope`, if `storeErr` is true, return 503 Service Unavailable; if `!allowed`, return 429 Too Many Requests with `Retry-After`; return 403 only when the limiter admits the request.
- **Recommended fix:** Check `storeErr` (503) and `!allowed` (429 with `Retry-After`) on the `!valid` and `!hasScope` limiter branches before returning 403.
- **Verification:** `go test ./internal/interface/cron/admin/... -run TestRateLimit -count=3` with subtests asserting 429 and 503 outcomes on invalid-subject and missing-scope bootstrap attempts.

### CR-004 — isControlShape misclassifies multi-segment paths under /api/jobs/ as allowed reads [Low] [Confirmed]
- **Location:** `internal/interface/cron/admin/server.go:68-74` — `isControlShape`
- **Issue:** `isControlShape` evaluates `segment, _, _ := strings.Cut(rest, "/"); return segment == ""`. For multi-segment paths such as `/api/jobs/123/subpath` or `/api/jobs/123/run`, `segment` is `"123"`, returning `false` (allowed read).
- **Why it matters:** An unknown multi-segment path under `/api/jobs/` that gets rate-limited in `limitEnforce` will be classified as an allowed read instead of a control/unknown shape, causing it to fail silently without the mandatory security audit event.
- **Evidence:** The delimiter presence boolean `found` is discarded at line 72. Allowed reads are strictly `/api/jobs/{id}` where no trailing delimiter exists.
- **Plan violation:** E09.1-T02-R02, E09.1-T02-R05.
- **Expected behavior:** Multi-segment paths (where `hasMore` is true) must evaluate as control/unknown shapes (`isControlShape == true`) so they are audited when rate-limited.
- **Recommended fix:** Check `hasMore`: `segment, _, hasMore := strings.Cut(rest, "/"); return segment == "" || hasMore`.
- **Verification:** Unit test asserting `isControlShape("GET", "/api/jobs/123/subpath") == true`.

### CR-005 — corsStripWriter does not strip headers if upstream calls Write without WriteHeader [Low] [Risk]
- **Location:** `internal/interface/cron/admin/server.go:641-655` — `corsStripWriter`
- **Issue:** `corsStripWriter` embeds `http.ResponseWriter` and overrides `WriteHeader(code)` but does not implement `Write([]byte) (int, error)`. If an upstream handler writes directly via `w.Write` without calling `w.WriteHeader` first, standard Go `http.ResponseWriter` calls its underlying `WriteHeader(200)` directly, bypassing `corsStripWriter.WriteHeader`.
- **Why it matters:** Although `forward` deletes the request `Origin` header, any upstream handler setting `Access-Control-*` headers and writing body bytes without explicit `WriteHeader` risks emitting unstripped CORS headers.
- **Evidence:** `corsStripWriter` struct definition lacks a `Write` method.
- **Plan violation:** E09.1-T02-R03.
- **Expected behavior:** Header stripping should execute before any response bytes are written regardless of whether `WriteHeader` was called explicitly.
- **Recommended fix:** Implement `Write([]byte) (int, error)` on `corsStripWriter` with a guard ensuring headers are stripped before dispatching to the underlying `Write`.
- **Verification:** Unit test with an upstream handler that sets `Access-Control-Allow-Origin: *` and calls `w.Write` directly.

### CR-007 — Session TTL clamping if-statement can be modernized with built-in min [Low] [Confirmed]
- **Location:** `internal/interface/cron/admin/server.go:468-471` — `adminHandler.bootstrapTTL`
- **Issue:** `bootstrapTTL` bounds session TTL using a manual branch:
  ```go
  ttl := time.Until(sourceExpiry)
  if ttl > h.sessionCap {
      ttl = h.sessionCap
  }
  ```
  instead of utilizing the modern Go standard library built-in `min`.
- **Why it matters:** Idiomatic modern Go (Go 1.21+, baseline Go 1.27.1) expresses bounded clamping concisely with `min`.
- **Plan violation:** `docs/development/go-conventions.md` §Go idioms and toolchain ("Prefer standard-library slices, maps, cmp, log/slog, and testing facilities").
- **Expected behavior:** Modernize the clamping logic:
  ```go
  ttl := min(time.Until(sourceExpiry), h.sessionCap)
  ```
- **Recommended fix:** Replace the `if ttl > h.sessionCap` branch with `ttl := min(time.Until(sourceExpiry), h.sessionCap)`.
- **Verification:** Unit test `TestSessionBootstrap/configured_ttl_caps_the_cookie` passes.
