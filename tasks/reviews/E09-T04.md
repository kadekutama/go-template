## Findings

### CR-001 — API-key Verify/Rotate row lookups bypass RLS tenant scoping [High] [Confirmed]
- **Location:** `internal/infrastructure/auth/apikey/manager.go:218-240` — `Manager.findRow`
  (same pattern in `Manager.load`, `manager.go:308-316`)
- **Issue:** `findRow` and `load` run `m.db.WithContext(ctx)` queries without ever setting
  the RLS GUC (`app.current_tenant`), while migration `20260923000007_api_keys.sql:26-30`
  applies `FORCE ROW LEVEL SECURITY` with `USING (tenant_id =
  current_setting('app.current_tenant', true)::uuid)`. `rls.ApplyTenant` runs only inside
  `postgres.WithinTenantTx` (`postgres/tx_runner.go:49-55`), which these read paths
  deliberately do not use (Round-3 change: "removed transactions on read-only queries").
- **Why it matters:** Under the repository's documented production posture (ADR-016
  dynamic `app_user` leases, ADR-020 "RLS-enforced"), the connecting role is subject to
  RLS. With the GUC unset, `current_setting(..., true)` returns NULL → the policy filters
  every row → `Verify` returns `ErrNotFound` for **every valid key**, and `Rotate`'s
  `load` fails identically. The adapter fails closed in its primary function. Tests pass
  only because the Testcontainers connection is the Postgres superuser, which always
  bypasses RLS regardless of FORCE.
- **Evidence:** No `set_config` call exists outside `WithinTenantTx` (grep of
  `app.current_tenant` across `internal/`); `findRow`'s doc comment explicitly expects
  RLS to scope the pre-row lookup ("so RLS can scope the lookup before the row is known")
  but never applies it. `tasks/tracking/GATES.md:47` leaves "RLS adversarial test passes"
  open — exactly the check that would have caught this.
- **Plan violation:** E09-T04-R02 ("Verify … MUST fail closed on unknown/expired/revoked
  keys" — it fails closed on *everything* for non-superusers); ADR-020 §3 (tenant
  transaction runner discipline).
- **Expected behavior:** Row reads are tenant-scoped like every other E09 adapter: run
  `findRow`/`load` inside `postgres.WithinTenantTx(ctx, m.db, tenant, …)` (the tenant is
  already parsed from the plaintext hint before the query), or apply the GUC explicitly
  for the read path.
- **Recommended fix:** Wrap `findRow` and `load` in `WithinTenantTx`; keep the write paths
  as they are.
- **Verification:** Integration test connecting as a non-superuser, non-owner role: (a)
  `Verify` succeeds for a valid tenant key; (b) a foreign-tenant plaintext yields
  `ErrNotFound`; wire the case into `./tasks/scripts/gate-check.sh G4`.

### CR-008 — `Rotate` uses two independent transactions and a silent 1h window default [Low] [Confirmed]
- **Location:** `internal/infrastructure/auth/apikey/manager.go:279-304` — `Manager.Rotate`
- **Issue:** Successor creation (`m.Create` → its own `WithinTenantTx`) and the old key's
  `rotates_at` update (second `WithinTenantTx`) are not atomic; a crash between them
  leaves the successor live with the old key never scheduled for expiry. Additionally
  `window == 0 → time.Hour` is a silent default (`RotationWindow` carries only
  `validate:"gte=0"`), contradicting the zero-silent-defaults doctrine (ADR-021, Proposed).
- **Why it matters:** A partially applied rotation extends the old key's validity
  indefinitely (until revoked) — a bounded but real security-window drift; the silent
  default means an unconfigured window is a value no operator chose.
- **Evidence:** `Rotate` calls `m.Create(...)` (transaction 1) and then a separate
  `WithinTenantTx` for `rotates_at` (transaction 2); the zero-window branch is explicit
  in code.
- **Plan violation:** E09-T04-R04 intent (deterministic dual-active window); ADR-021 §1
  (proposed).
- **Expected behavior:** One transaction mints the successor and stamps `rotates_at`; a
  zero/absent window fails construction or is explicitly configured.
- **Recommended fix:** Merge both writes into one `WithinTenantTx`; require a positive
  `RotationWindow` (or document the default in the packet amendment).
- **Verification:** Test with a failing second step (tx error injection) asserting both
  operations roll back together; constructor case for zero window.

### CR-009 — Transparent hash upgrade writes outside the tenant GUC and swallows errors [Low] [Confirmed]
- **Location:** `internal/infrastructure/auth/apikey/manager.go:193-207` — `Manager.Verify`
  upgrade path
- **Issue:** The re-hash `UPDATE` runs on `m.db.WithContext(ctx)` without the RLS GUC (see
  CR-001) and its error is discarded (`_ = …`), so under the production posture the
  upgrade silently becomes a no-op (0 rows updated) with no signal.
- **Why it matters:** No security loss (the old hash still verifies), but the parameter
  migration/upgrade flow (version tag → active params) never persists, and the design's
  "transparently re-hash and persist" contract silently degrades.
- **Evidence:** Same unset-GUC analysis as CR-001; `_ =` discard is explicit in the code.
- **Plan violation:** E09-T04-R02 partial (verify/upgrade behavior); none direct.
- **Expected behavior:** The upgrade write runs in the same tenant scope as the read and
  reports failures (or is retried) rather than being discarded.
- **Recommended fix:** Perform read+verify+upgrade inside one `WithinTenantTx`, or remove
  the silent upgrade until the read path is scoped.
- **Verification:** Integration test as non-superuser: seed a v1-sealed hash, verify with
  active v1 params, assert the stored `version`/columns changed (today they will not).
