# Epic E09.3: Log Delivery, Dependency & Test-Harness Maintenance

**Status:** completed
**Story Points:** 7
**Phase:** 5.3
**Dependencies:** E01, E09.2
**SDD Gate:** G4
**Design refs:** `SPEC.md §2`, `SPEC.md §7.9`, `docs/architecture/ADR-012-owner-directed-e01-defaults.md`, `docs/development/go-conventions.md`

> Why this maintenance epic: the platform already routes structured zerolog
> records through the kernel `log.Logger` port, but the binary bootstrap only
> writes to stdout and test fixtures deliberately discard log output. The
> repository owner requested (2026-10-22) that local runs keep logs visible in
> the terminal, while server environments write newline-delimited JSON to
> rotating files that a log processor can tail and ship. The same owner
> request refreshes the Go patch release and six direct dependency pins. This
> epic keeps those operational changes isolated from the completed functional
> epics and does not reopen E09.2.

## Tasks

### E09.3-T01: Go 1.27.3 refresh + environment-aware rotating log delivery
**Status:** completed
**Background:** Local development currently sends all logs to stdout, which is
correct, but the same behavior is used in server environments and test helpers
hide logs with `io.Discard`. Servers need durable, rotated, structured files
that a log-processor sidecar can tail; local runs need visible terminal output.
The Go toolchain and five direct modules also need their requested patch/minor
updates.
**Files:**
- Modify: `go.mod`, `go.sum`, `.github/workflows/ci.yml`, `SPEC.md`, `AGENTS.md`, `docs/development/go-conventions.md`
- Modify: `internal/infrastructure/logging/**`, `internal/shared/di/infrastructure.go`, `internal/shared/di/fxlifecycle.go`, `internal/shared/di/di_test.go`
- Modify: `internal/infrastructure/config/config.go`, `internal/infrastructure/config/config_test.go`, `config/config.yaml`, `config/config.staging.yaml`, `config/config.production.yaml`, `config/config.local.yaml.example`, `config/schemas/config.json`
- Modify: `.env`, `.env.example`, `.env.staging.example`, `.env.production.example`
- Modify: `internal/infrastructure/profiling/*_test.go`, `internal/infrastructure/coordination/etcd/etcd_test.go`
- Create: `docs/architecture/ADR-028-file-based-log-delivery.md`, `deployments/logging/vector.yaml`
- Modify: `docs/architecture/README.md`, `docs/infrastructure/README.md`
**Steps:**
1. Pin Go `1.27.3` in `go.mod`, CI, and normative docs.
2. Upgrade `pressly/goose/v3` to `v3.29.0`, `golang.org/x/text` to `v0.43.0`, `twmb/franz-go` to `v1.22.2`, `golang.org/x/crypto` to `v0.58.0`, and `golang.org/x/sync` to `v0.24.0`; run `go mod tidy` and `go mod verify`.
3. Extend the logging adapter with validated `stdout`, `file`, and `both` output modes, rotating JSON file output (`lumberjack`), and environment resolution that defaults to stdout locally and rotating files for staging/production with an explicit file path.
4. Keep the entrypoint logger and the fx graph on the same writer instance so file mode never opens competing rotators.
5. Replace test logger `io.Discard` sinks with visible output and enable the etcd fixture's log level; retain `io.Discard` only for HTTP response-body draining.
6. Add synchronized YAML/JSON-schema/env documentation, a Vector log-processor sample, and an ADR for file-based delivery.
**Acceptance Criteria:**
- [x] Go 1.27.3 and the five requested dependency versions are pinned; `go mod verify`, build, race tests, and lint pass.
- [x] Local/default logging writes directly to the terminal; staging/production default to a validated rotating JSON file; `both` is supported.
- [x] No test logger sink uses `io.Discard`; only HTTP body drains remain.
- [x] The server file path and rotation settings are documented and schema-aligned, with a log-processor handoff sample.

### E09.3-T02: NATS testcontainer host-connect readiness
**Status:** completed
**Background:** E09.3-T01 closeout disclosed a local parallel-suite NATS
readiness race: `StartNATS` waits only for the container log line
`Server is ready`, then returns the mapped URL before Docker's host endpoint is
guaranteed to accept a NATS client. The owner directed the fix to remain in the
shared testcontainers harness and explicitly excluded changes to the production
NATS publisher or its fail-fast behavior.
**Files:**
- Modify: `test/testcontainers/nats.go`, `test/testcontainers/harness_test.go`
**Steps:**
1. Combine the container `Server is ready` log wait with a mapped listening-port wait.
2. Probe the mapped URL with a real, bounded NATS client handshake before returning the handle; close the probe connection on success.
3. Terminate the container and return a descriptive error when the readiness bound expires.
4. Add a harness smoke assertion that an immediate connection to the returned URL succeeds.
**Acceptance Criteria:**
- [x] `StartNATS` returns only after a host-side NATS handshake succeeds.
- [x] Failure to become reachable terminates the container and returns an error.
- [x] The harness smoke test proves an immediate connection can be established.
- [x] No production client, Compose, or integration-test source changes are made.
- [x] Focused/race tests, lint, full-suite/G4, and SDD checks pass or any external environmental limitation is recorded.
**Story Points:** 2
**Depends On:** E09.3-T01, E07-T09
**Related Docs:** `tasks/specs/E07-T09.md`, `tasks/evidence/E09.3-T01.md#NATS flake evidence and owner acceptance`
