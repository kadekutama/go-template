# Task Specification: E03-T11 — Payout Eligibility, Reserves, and Negative-Balance Recovery

**Task:** E03-T11  
**Spec Status:** draft  
**Author:** repository-audit-agent  
**Reviewer:** unassigned  
**Last Updated:** 2026-09-11

## Objective

Make payout eligibility and negative-balance recovery explicit, durable, and
testable so returns, disputes, or fees cannot create an unbounded payout loss.

## Scope

### In Scope

- Per-tenant/asset payout minimums, first-payout hold, rolling reserve, instant
  eligibility, and strong-cursor available-balance decisions.
- A durable recovery workflow using a verified external instrument, provider
  idempotency/status lookup, audit facts, and balanced recovery postings.

### Out of Scope

- Provider HTTP adapters and transport handlers (E06/E10/E11).
- Persistence schema/transaction implementation (E07) beyond the port contract.
- Jurisdiction-specific collections policy; it must be supplied as versioned
  configuration rather than invented by this task.

## Requirements

| ID | Requirement | Priority |
|----|-------------|----------|
| E03-T11-R01 | Eligibility MUST evaluate the strong PostgreSQL balance projection at a supplied cursor and apply the configured minimum, first-payout hold, rolling reserve, instant-method, and destination-verification policies. | must |
| E03-T11-R02 | An ineligible payout MUST return `PAYOUT_BLOCKED` with a stable reason and MUST NOT create a provider submission or mutate a Posting/Entry. | must |
| E03-T11-R03 | Recovery MUST be keyed by tenant, account, asset, and idempotency key; a repeated fingerprint MUST replay the original outcome and a different fingerprint MUST conflict. | must |
| E03-T11-R04 | A provider timeout MUST enter `OUTCOME_UNKNOWN` and MUST require status lookup before any retry that could move money. | must |
| E03-T11-R05 | Confirmed recovery MUST produce a balanced, linked posting plus audit and outbox facts; it MUST NOT update a mutable account balance column. | must |

## Executable Scenarios

| ID | Given | When | Then |
|----|-------|------|------|
| E03-T11-S01 | A new tenant inside the seven-day first-payout hold | A payout is requested | The command returns `PAYOUT_BLOCKED` with `FIRST_PAYOUT_HOLD`; no external call or posting occurs. |
| E03-T11-S02 | An account with available funds below its rolling reserve or below zero | A payout is requested | The command returns `PAYOUT_BLOCKED` with the policy reason and starts no duplicate recovery workflow. |
| E03-T11-S03 | A negative balance and a verified bank instrument | Recovery is requested twice with the same fingerprint | One durable attempt exists and both calls return the same result. |
| E03-T11-S04 | A provider times out after accepting the recovery request | The worker retries | It first resolves provider status by provider idempotency key; no blind second submission occurs. |
| E03-T11-S05 | Provider status confirms collection | Recovery is committed | One balanced funding/offset posting, audit record, and outbox event commit atomically. |

## Interfaces and Data

- `PayoutPolicy` is a domain value object keyed by tenant and `AssetCode`; all
  rates, dates, and minimums are versioned configuration.
- `RecoveryAttempt` contains tenant/account/asset IDs, durable idempotency key,
  provider idempotency key, status, reason, provider trace ID, actor/evidence,
  and timestamps. Public DTOs expose status/reason, not provider secrets.
- The application maps `PAYOUT_BLOCKED` and `OUTCOME_UNKNOWN` to the existing
  error envelope; E07 owns the transaction and uniqueness constraints.

## Invariants and Failure Semantics

- Eligibility and recovery decisions are tenant-scoped and use PostgreSQL
  authority; Valkey and lagging replicas are hints only.
- Payout policy may block a negative available balance without declaring the
  immutable historical Posting invalid.
- Recovery effects are at-least-once and deduplicated by durable keys. Unknown
  outcomes remain unresolved until provider lookup; cancellation is explicit.
- Recovery postings balance independently per asset and preserve reversal/audit
  linkage. No direct SQL or ORM update may rewrite posted facts.
