## Objective

Provide one reviewable runtime flag boundary for payment methods, currencies, HTTP/3, and kill switches behind a consumer-owned `FlagClient` port, with an OpenFeature + Unleash adapter, a Valkey/in-memory fallback that serves last-known/defaults when Unleash is down, and E09.1 egress-permit + E01-T08 resilience composition on every outbound attempt — so E11–E14 never block on vendor access.

## Scope

### In Scope

This file is additive; E06-T12 owns the other 23 port files and did not define `FlagClient` (see Normative Inputs conflict C01).

## Invariants and Failure Semantics

- Flags are non-authoritative hints (ledger-core §8 analogue): kill switches and method/currency gates may change display/routing behavior but MUST NOT rewrite postings, balances, or idempotency records.
- Unknown provider outcomes surface as typed errors with the fallback value; callers decide (fail-open on defaults vs fail-closed on last-known) — the adapter MUST NOT hide staleness (returns `Fallback:true`/`Stale:true` markers).
- Timeouts via caller context deadlines; breaker counts timeouts as failures; limiter errors never count as breaker failures.
- Refresh is bounded (10s); concurrent evaluations share one in-flight fetch per flag key only where safe — money-moving coalescing rules do not apply (flags are cacheable reads), but cross-scope credential/response sharing is forbidden.
- Secrets (Unleash admin/client keys) come from config/secret references only; they MUST NOT appear in logs, errors, or evidence fixtures.

## Test Convention Exception (2026-10-13)

Per `AGENTS.md` Unit Test Structure §7 (return-value cardinality), the
permit-per-attempt (R04/S07), fail-closed no-unmetered-call (R05/S05), and
breaker fast-fail (R06/S06) proofs require inspecting test-double internals
(egress `Wait` call counts and keys, `Doer.Do` call counts, breaker state)
alongside the function's return tuple. These side effects cannot be verified
through return values alone: a limiter failure and a provider failure both
yield fallback + typed error, so the return tuple cannot distinguish
"metered then failed" from "unmetered". The unit suite therefore adds, for
those scenarios only, one call-count/key assertion per table case in addition
to the exact return-arity assertions. All other scenarios assert return arity
exactly with no implementation-detail checks.
