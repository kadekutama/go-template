### E09.2-T01: Pure generic collection helpers (`samber/lo` v1.53.0) + `depguard`/`forbidigo` guardrails + codebase refactoring
**Status:** completed
**Background:** Even with Go 1.27's standard-library `slices`, `maps`, and `cmp` packages, domain services, application sagas, and SQL repositories contain repetitive multi-line loops for slice-to-map indexing (`KeyBy`), grouping (`GroupBy`), deduplicated extraction (`UniqMap`), set operations (`Union`, `Difference`), and infallible slice projections (`Map`, `Filter`). Strictly speaking from Clean Architecture and SOLID principles, importing a pure, stateless, zero-dependency generic functional utility library (`github.com/samber/lo v1.53.0`) in `internal/domain/` and `internal/application/` does not violate the Dependency Rule—provided impure concurrency/retry helpers (`lo/parallel`, `lo.Attempt*`, `lo.Async*`, `lo.Transaction*`, `lo.NewDebounce*`, `lo.Synchronize*`, `lo.WaitFor*`) are mechanically banned by the linter so `internal/shared/kernel/safe` and `internal/infrastructure/resilience` remain the sole concurrency and retry mechanisms.

### E09.2-T03: Interprocedural static nil-safety verification (`uber-go/nilaway`) + zero-finding remediation
**Status:** completed
**Background:** Standard `go vet` and `staticcheck` (`SA5011`) only detect intraprocedural nil dereferences within a single function body. Uber's `go.uber.org/nilaway` (`@latest`) performs interprocedural static nil-flow analysis across package boundaries, catching nil pointer returns from repositories, unguarded map/slice lookups, and partially initialized struct pointers on error paths before they can cause a production panic (`SPEC.md §9.7` panic budget: zero production panics).Note: running `nilaway` as a standalone `go/analysis` driver (`make nilaway`) avoids `golangci-lint` memory bloat while enforcing strict interprocedural checks in `make lint`, `make verify`, and CI.
**Files:**
- Modify: `scripts/dev/setup.sh`, `Makefile`, `.github/workflows/ci.yml`, `SPEC.md`
- Modify (as needed for nil-flow remediation): production `.go` files under `internal/`, `pkg/`, and `cmd/` flagged by `nilaway`
**Steps:**
1. In `scripts/dev/setup.sh`, add `"nilaway:go.uber.org/nilaway/cmd/nilaway@latest"` to the `GO_TOOLS` array so `./scripts/dev/setup.sh` installs and links `nilaway` into `~/.pixi/bin`.
2. In `Makefile`:
   - Add a `nilaway` phony target:
     ```makefile
     nilaway: ## Run Uber NilAway interprocedural nil-safety analyzer
     	@echo "Running nilaway..."
     	@nilaway -include-pkgs="github.com/kadekutama/go-template" -test=false ./internal/... ./pkg/... ./cmd/...
     ```
   - Add `nilaway` to the `lint` target prerequisites/recipe (after `gopls-check` and `golangci-lint run ./...`) so `make lint` and `make verify` enforce zero `nilaway` findings.
3. Update `.github/workflows/ci.yml` in the `lint` job to install and execute `make nilaway` (or run via `make lint`).
4. Run `make nilaway` across `./internal/... ./pkg/... ./cmd/...` and remediate every reported nil-flow finding in production code (e.g., adding explicit nil guards, returning typed sentinel/validation errors, or ensuring error-path returns never dereference nil receivers/pointers). Never silence findings by disabling `nilaway` on production packages.
**Acceptance Criteria:**
- [ ] `scripts/dev/setup.sh` installs `nilaway` (via `@latest`) into `~/.pixi/bin/nilaway`.
- [ ] `make nilaway` and `make lint` pass with **0 findings** across `./internal/... ./pkg/... ./cmd/...`.
- [ ] All unit tests pass (`go test -v -race ./...`) after any nil-safety remediations.

### E09.2-T04: Continuous profiling adapter (`grafana/pyroscope-go` v1.4.3 + `otel-profiling-go` v0.7.0) & OTel span-profile correlation
**Status:** completed
**Background:** Distributed traces (`internal/infrastructure/tracing/otel.go`) show slow spans in Tempo (`SPEC.md §7.9`), but cannot attribute latency or memory pressure to specific Go functions, heap allocations, or mutex contention inside a span without continuous profiling. Adopting `github.com/grafana/pyroscope-go v1.4.3` and `github.com/grafana/otel-profiling-go v0.7.0` in a dedicated `internal/infrastructure/profiling/` adapter wraps the OpenTelemetry `TracerProvider` so every sampled root span carries a `pyroscope.profile.id` tag linked to CPU, `alloc_objects`, `alloc_space`, `inuse_objects`, `inuse_space`, `goroutines`, `mutex_count`, `mutex_duration`, `block_count`, and `block_duration` profiles. The adapter is disabled by default (`observability.profiling.enabled: false`), follows the Parameter Object pattern (`ProfilerParams` + `NewProfiler`), and manages lifecycle startup/flush/stop cleanly via `fx.Lifecycle`.

- Modify: `internal/infrastructure/tracing/otel.go`, `internal/infrastructure/tracing/otel_test.go`, `internal/shared/di/infrastructure.go`, `internal/shared/di/di_test.go`
