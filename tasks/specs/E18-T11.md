## Objective

Give wrong or misunderstood review findings a clean place to die by defining
a two-channel feedback loop — implementer dispositions in the handoff,
reviewer adjudication in the report — with reviewer rejection rights and a
final owner override.

## Scope

### In Scope

- SDD §3.4 sentences: implementer reply location/format, reviewer
  adjudication with contest-rejection rights, terminal finding states, and
  owner-only override of held findings.
- Handoff template `## Code Review` section: per-finding reply format (state,
  reason, evidence, details).
- Reviewer prompt adjudication paragraph: read handoff dispositions first on
  re-invocation, withdraw or hold with reasoning, update only Resolution
  Notes (plus Verdict fields to match), never touch Findings or the handoff.
- Task index/progress totals.

### Out of Scope

- Frontmatter, validator, template, or other SDD section changes.
- Any implementation (non-test Go), migration, contract, or E09 change.

## Normative Inputs

- `tasks/SDD.md` §3.4 (completion items 3–4), §4 step 7.
- `tasks/handoffs/_TEMPLATE.md` `## Code Review` section.

- Owner direction 2026-09-28: implementer states state/reason/details;

## Requirements

| ID | Requirement | Priority |
|----|-------------|----------|
| E18-T11-R01 | The implementer MUST reply per finding ID in the handoff `## Code Review` section, each entry stating state (`fixed` with verifying commit/test, or `contested`), reason, counter-evidence with file:line where applicable, and any details the reviewer needs to adjudicate; the implementer MUST NOT edit the review report. | must |
| E18-T11-R02 | The reviewer MUST adjudicate each contested finding in `## Resolution Notes` — withdraw with reason or hold with rebuttal grounded in packet/normative sources — and MAY reject an implementer contest that does not stand; the reviewer MUST NOT edit `## Findings` or the handoff. | must |
| E18-T11-R03 | On adjudication the reviewer MUST update Verdict/Final Review Status to match the adjudicated state so the completion gate reflects reality. | must |
| E18-T11-R04 | Only the repository owner MAY overrule a held finding, by explicit recorded decision with rationale; the overrule is recorded as ACCEPTED by owner and is final. | must |
| E18-T11-R05 | Every finding MUST reach a terminal state — FIXED, WITHDRAWN, ACCEPTED (named acceptor), or OPEN — and any OPEN finding above Low blocks completion. | must |
| E18-T11-R06 | Index/progress totals MUST include E18-T11; no other file may change. | must |

## Executable Scenarios

| ID | Given | When | Then |
|----|-------|------|------|
| E18-T11-S01 | A finding the implementer believes is a misunderstanding | Implementer replies | Handoff carries a contested entry with reason and counter-evidence; the report is untouched. |
| E18-T11-S02 | A contested entry the reviewer finds baseless | Reviewer is re-invoked | Resolution Notes hold the finding with rebuttal; Findings and handoff unchanged; verdict still blocks if Medium+. |
| E18-T11-S03 | A held finding the owner explicitly overrules | Owner decides | Resolution Notes record ACCEPTED by owner with rationale; the task may complete. |

## Invariants and Failure Semantics

- Single-writer rule: implementer writes handoff dispositions; reviewer writes
  report notes. Neither rewrites the other's text; findings are immutable once
  written (withdrawal happens via notes, not edits).
- Chat discussion is non-authoritative; only the two durable records count.
- Released E18-T06/T07/T08/T09/T10 artifacts stay frozen.
