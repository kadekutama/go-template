### NATS flake evidence and owner acceptance

The default parallel full-suite and `make test-all` attempts reported only:

```text
--- FAIL: TestNATSFanout
    nats: no servers available for connection
--- FAIL: TestPublisherPublishEventValidation
    nats: connect: nats: no servers available for connection
FAIL github.com/kadekutama/go-template/test/integration/messaging
```

A subsequent exact `go test -v -race -count=1 ./...` run failed at
`messaging_test.go:161` (`TestNATSFanout`), and a CI-equivalent
`go test -race -count=1 ./...` rerun failed at `messaging_test.go:254`
(`TestPublisherPublishEventValidation`). The failing test shifted between runs;
every other package passed. The messaging package passed immediately in
isolation:

```text
ok github.com/kadekutama/go-template/test/integration/messaging 5.932s
```

The local Docker engine is Rancher Desktop WSL (`Server Version: 29.5.3`,
`Total Memory: 15855 MB`). The NATS helper waits for the log line
`Server is ready` but not for the mapped client port to accept connections;
under concurrent package/container startup, `nats.Connect` can race that
readiness handoff. No NATS, messaging, or `test/testcontainers` implementation
file was changed by E09.3-T01, and fixing that pre-existing harness race is
outside this packet's change surface.

The repository owner confirmed on 2026-10-22 that integration tests, including
GitHub CI, have no failures and that other harnesses report no problems. That
CI/owner evidence, together with the serialized full-suite and G4 passes,
establishes that this is a local Rancher Desktop/testcontainers readiness
limitation rather than an E09.3 regression or an unresolved integration-test
failure. The owner accepted this evidence for closeout; the local parallel
failure remains disclosed here and is not claimed as a green local invocation.
A separate harness-hardening task could replace the NATS log-only wait with a
listening-port wait, but that change must not be made under this released
claim.
